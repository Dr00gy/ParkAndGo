# ParkAndGo — Consistency Checks

This document checks the consistency between the ParkAndGo code, project documentation, and the UML use-case/state diagrams.

| Check | What the code says | What the diagrams / text say | Analysis | Status / Recommended action |
|---|---|---|---|---|
| **1. Create vs. Confirm** | `create_draft()` validates the time, duration, etc., then creates a reservation with state **`DRAFT`**. It does **not** reserve the parking space. `confirm()` later checks for overlapping `CONFIRMED` reservations and changes the state to **`CONFIRMED`**. | The use-case diagram has **Create Reservation** and **Confirm Reservation** as separate use cases. The Project Frame explicitly says “Create reservation or just a draft of it.” | The implementation has a clear two-step lifecycle: **Create → DRAFT → Confirm → CONFIRMED**. The resource is considered reserved only after confirmation. The name **“Create Reservation”** could nevertheless suggest that the spot is already reserved. | 🟢 **Consistent.** For clarity, rename the use case to **“Create Draft Reservation”** or explicitly document that Create does not allocate the resource. |
| **2. Availability vs. Confirm** | `check_availability()` checks operating hours and calls `_has_overlapping_confirmed()`. `confirm()` uses the same `_has_overlapping_confirmed()` check before confirming. Only **`CONFIRMED`** reservations block availability. | The diagram has **Check Availability** and **Confirm Reservation** as separate operations. The Project Frame says confirmed reservations must not overlap. | The blocking rule is consistent: both operations use the same definition of an occupied slot. A `DRAFT` reservation does **not** make the spot unavailable, which matches the state semantics in the documentation. A remaining technical issue is possible concurrency: two confirmations could theoretically pass the read-then-write check at the same time. | 🟢 **Consistent**, with a known concurrency risk. The existing scale note correctly identifies this as a future concern. |
| **3. Cancel vs. State Diagram** | `cancel()` allows cancellation when the reservation is **`DRAFT` or `CONFIRMED`**. It rejects an already `CANCELLED` reservation. It then changes the state to `CANCELLED`. | The state diagram shows **both DRAFT and CONFIRMED → Verifying Cancellation → CANCELLED/Rejected**. The Project Frame says `DRAFT → CONFIRMED → CANCELLED`. | Contrary to the suspected problem, the supplied state diagram **does allow cancellation from CONFIRMED**: the arrow from `CONFIRMED` goes to `Verifying Cancellation`. The code and diagram therefore agree. | 🟢 **No contradiction found.** It would still be clearer to explicitly label the successful transitions as `DRAFT → CANCELLED` and `CONFIRMED → CANCELLED`. |
| **4. Meaning of time intervals** | `_has_overlapping_confirmed()` uses `existing.start_time < requested.end_time` and `existing.end_time > requested.start_time`. This implements a **half-open interval**, effectively `[start,end)`. Tests verify that `09:00–10:00` and `10:00–11:00` can coexist. | The Project Frame describes a reservation period but does not explicitly define `[start,end)` semantics. | The implementation and tests are internally consistent with **half-open intervals**. This matters because a closed interval would incorrectly treat `10:00–11:00` as overlapping `09:00–10:00`. | 🟡 **Implementation is consistent, specification is underspecified.** Add an explicit rule: **“Reservation intervals are interpreted as `[start_time, end_time)`; a reservation ending when another begins does not overlap.”** |
| **5. Use-case diagram vs. project text** | The service layer implements **create, confirm, cancel, check availability, and prolong**. The API also implements accounts, login, registration, “my reservations,” etc. | The use-case diagram shows **Create Reservation, Check Availability, Confirm Reservation, Cancel Reservation**, plus the Notification Service. It does **not show Prolong Reservation**. The Project Frame explicitly lists **“Prolong reservation”** as a core operation. | This is the clearest diagram/specification mismatch. **Prolong** is explicitly part of the core domain and is implemented in the code, but it is missing from the use-case diagram. There is also a naming issue: the diagram says “Create Reservation,” while the code actually creates a draft. | 🟢 **Functionality correctly apparent.** **Create Draft Reservation** and **Prolong Reservation** is now a clear part of the UC diagram. |
| **6. Requirement vs. design decision** | The project uses **SQLite + SQLAlchemy**. The architecture documentation explains why SQLite was chosen instead of PostgreSQL: no separate server is required and it is sufficient for the current scope. PostgreSQL is mentioned only as a possible future replacement if scale increases. | The Project Frame contains no requirement saying that PostgreSQL must be used. The architecture document treats database choice as a design decision. | There is no evidence that **“Use PostgreSQL” is a requirement**. The requirement is persistent storage; SQLite is the current implementation choice. PostgreSQL may become appropriate later, but that is not currently a requirement. | 🟢 **Correct separation.** Keep **“persistent relational storage”** as the requirement and **SQLite** as the current design decision. |
| **7. Uncertainty vs. invented precision** | The code contains concrete values: **06:00–23:00 operating hours, 30-minute increments, 4-hour maximum duration**. It also has a future-scale assumption of **10× concurrent requests** and simulated notification timeout/failure behavior. | The Project Frame explicitly documents 06:00–23:00, 30-minute increments and 4-hour maximum. The architecture document calls the 30-minute/4-hour values **reasonable defaults**. The future pressure explicitly says **10×** concurrency. | These values are **not unexplained AI inventions**: they are documented project decisions or assumptions. However, they are not all externally justified requirements. In particular, “4 hours” is described as a reasonable default, not necessarily a stakeholder requirement. The 10× value is a future-pressure scenario, not measured production traffic. | 🟢 **No unsupported precision found**, but assumptions should be labelled clearly. Distinguish **requirement**, **assumption**, **design decision**, and **test/scenario value**. |
